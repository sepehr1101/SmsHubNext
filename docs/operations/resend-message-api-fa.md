# ارسال مجدد یک پیامک

در `/admin/delivery-reports` یک پیام را انتخاب کنید. بخش «ارسال مجدد» مقصد را نمایش می‌دهد و پیش از ثبت هزینه جدید، تأیید می‌گیرد. پیام قبلی و سابقه تحویل آن حفظ می‌شوند؛ یک پیام و دسته تک‌پیامی جدید با وضعیت Queued و تعرفه فعال فعلی ساخته می‌شود. بدهی طبق قواعد موجود مجاز است؛ ارسال به سرویس‌دهنده توسط همان worker انجام می‌شود.

## API مشتری

`POST /messages/{messageId}/resend`

هدر `X-Api-Key` باید کلید معتبر مشتری باشد. کلید مدیر، JWT مدیریت و نشست مرورگر مجوز این endpoint نیستند. پنل مدیریتی از مرز احراز هویت موجود و همان handler استفاده می‌کند؛ برای اقدام مدیر، هزینه به مشتری پیام اصلی و ApiKeyId به کلید واقعی مدیر نسبت داده می‌شود.

بدنه JSON:

```json
{
  "requestId": "5f826368-dc30-46a1-82e0-f42a51ec2475"
}
```

UUID جدید به معنی درخواست آگاهانه ارسال جدید است. اگر پاسخ HTTP قطع شد، **همان UUID** را با همان شناسه پیام تکرار کنید. کلید تکرار در محدوده مشتری و پیام اصلی است. درخواست‌های هم‌زمان با کلید یکسان فقط یک پیام و یک بدهکارسازی جدید ایجاد می‌کنند. در پنل نیز UUID در طول همان اقدام ثابت می‌ماند؛ پس از ثبت موفق، دکمه اقدام حذف و لینک پیام جدید نمایش داده می‌شود. بارگذاری مجدد صفحه یا انتخاب دوباره پیام یک اقدام جدید است؛ در پاسخ نامعلوم، بدون بررسی دسته‌های جدید، ارسال تازه‌ای را تأیید نکنید.

پاسخ HTTP 202 در پوشش استاندارد API:

```json
{
  "data": {
    "originalMessageId": 123,
    "messageId": 456,
    "batchId": 789,
    "isDuplicate": false
  }
}
```

پاسخ استاندارد شامل فیلدهای عمومی دیگر مانند success/error نیز هست؛ مثال فقط بخش data را نشان می‌دهد. 202 تأیید ثبت در صف است، نه تضمین ارسال یا تحویل. در بازپخش همان درخواست، شناسه‌ها ثابت و isDuplicate برابر true است.

## قواعد

- فقط پیام‌های خود مشتری قابل ارسال مجددند؛ پیام مشتری دیگر و شناسه ناموجود هر دو 404 می‌دهند.
- رد قطعی ارسال (`Rejected`) یا پیام پذیرفته/ارسال‌شده با نتیجه قطعی `Delivered`، `Undelivered` یا `Expired` مجاز است. پیام تحویل‌شده نیز با تأیید صریح کاربر قابل ارسال دوباره است.
- پیام در صف، در انتظار تأیید، دارای نتیجه ارسال نامشخص یا در انتظار گزارش نهایی، با 409 و `sending.resend_not_allowed` رد می‌شود.
- اگر متن طبق retention حذف شده باشد، 409 و `sending.resend_body_missing` برمی‌گردد؛ بازپخش درخواست قبلاً پذیرفته‌شده همچنان نتیجه قبلی را می‌دهد.
- متن، گیرنده، خط، طبقه‌بندی، منطقه، شناسه قبض و پرداخت از رکورد اصلی خوانده می‌شوند؛ کلاینت نمی‌تواند آن‌ها یا مشتری هدف را در این API تغییر دهد. خط، حساب سرویس، مشتری، منطقه و تعرفه دوباره با قواعد فعال فعلی اعتبارسنجی می‌شوند.
- `ClientBatchId` و `ClientCorrelatedId` پیام جدید قالب `resend:{originalMessageId}:{requestId بدون خط تیره}` دارند و پیوند ماندگار با پیام اصلی را حفظ می‌کنند. شناسه پیگیری قبلی کپی نمی‌شود؛ شناسه پیام/سرویس جدید برای ارسال تازه استفاده می‌شود.
- درخواست نامعتبر 400؛ کلید نامعتبر/مفقود 401؛ کلید مدیر در API مشتری 403؛ پیام غیرقابل مشاهده 404؛ وضعیت یا متن نامناسب 409. خطاهای اعتبارسنجی خط و تعرفه همان خطاهای ارسال عادی‌اند.

این قابلیت ارسال واقعی به سرویس را در درخواست HTTP انجام نمی‌دهد و وضعیت پیام قبلی را بازنشانی نمی‌کند. مهاجرت یا زیرساخت جدید ندارد.
