# API مشاهدهٔ پیام‌های مشتری

برنامه‌های بیرونی می‌توانند با همان کلید ارسال مشتری، پیام‌های ثبت‌شدهٔ آن مشتری را با شناسه قبض یا شماره تلفن پیدا کنند:

```http
GET /messages?billId=00123&fromJalali=1405/07/01&toJalali=1405/07/30
X-Api-Key: YOUR_CUSTOMER_API_KEY
```

این مسیر کلید مشتری را مستقلاً بررسی می‌کند؛ به JWT مدیر نیاز ندارد. کلید مدیر، ورود پنل یا JWT مدیریت جایگزین کلید مشتری نیست. انقضا، ابطال، فعال‌بودن مشتری/کلید و محدودیت IP همانند احراز هویت ارسال بررسی می‌شوند. مشتری از کلید احراز‌شده تعیین می‌شود؛ پارامتر `customerId` نمی‌تواند مشتری دیگری را انتخاب کند.

## پارامترها

| پارامتر | توضیح |
|---|---|
| `billId` | شناسه کامل قبض؛ حداکثر ۳۱ نویسه. صفرهای ابتدای مقدار حفظ می‌شوند. |
| `mobileNumber` | شماره کامل تلفن؛ قالب‌های `09…`، `989…` و `+989…` پذیرفته می‌شوند. |
| `fromJalali` | تاریخ شروع با قالب `1405/07/01`، الزامی و شامل همان روز. |
| `toJalali` | تاریخ پایان با همان قالب، الزامی و شامل همان روز. |
| `beforeDate` | برای صفحه بعد: مقدار `data.next.submitDateJalali` پاسخ قبلی. |
| `beforeId` | برای صفحه بعد: مقدار `data.next.id` پاسخ قبلی. |

دقیقاً یکی از `billId` یا `mobileNumber` لازم است. شناسه‌ها با مقدار کامل تطبیق داده می‌شوند؛ جست‌وجوی بخشی یا wildcard وجود ندارد. ارقام فارسی و عربی ورودی هم پذیرفته می‌شوند. تاریخ‌ها بر اساس کلید دورهٔ شمسی پیام (`SubmitDateJalali`، روز تهران در مسیر ثبت ارسال) فیلتر می‌شوند. هر صفحه حداکثر ۲۵ پیام دارد و با ترتیب نزولی `(SubmitDateJalali, Id)` بازگردانده می‌شود.

نمونهٔ درخواست با شماره تلفن:

```sh
curl --get 'https://YOUR_HOST/messages' \
  --header 'X-Api-Key: YOUR_CUSTOMER_API_KEY' \
  --data-urlencode 'mobileNumber=09120000001' \
  --data-urlencode 'fromJalali=1405/07/01' \
  --data-urlencode 'toJalali=1405/07/30'
```

برای شماره‌ای که با `+` شروع می‌شود، علامت مثبت باید URL-encode شود؛ `--data-urlencode` این کار را انجام می‌دهد.

## پاسخ و صفحه‌بندی

پاسخ از قالب معمول API استفاده می‌کند: `success`، `code`، `message`، `data` و `meta`. بخش `data` شامل `items` و `next` است. هر آیتم، شناسه پیام و دسته، تاریخ شمسی، زمان دقیق ثبت به UTC، شماره تلفن، شناسه قبض و پرداخت، نام مشتری و ارائه‌دهنده، وضعیت ارسال و تحویل، هزینهٔ ثبت‌شده و متن پیام را دارد.

نمونهٔ بخش `data` در پاسخی که صفحهٔ بعد دارد:

```json
{
  "items": [
    {
      "id": 12345,
      "messageBatchId": 987,
      "submitDateJalali": "1405/07/26",
      "submittedAtUtc": "2026-10-18T09:00:00Z",
      "mobileNumber": "989120000001",
      "billId": "00123",
      "payId": null,
      "customerName": "نام مشتری",
      "providerName": "نام ارائه‌دهنده",
      "status": 3,
      "deliveryStatus": 2,
      "totalCost": 1000.0000,
      "body": "متن پیامک"
    }
  ],
  "next": { "submitDateJalali": "1405/07/20", "id": 12300 }
}
```

نمونه برای اختصار فقط یک آیتم را نشان می‌دهد؛ در پاسخ واقعی، `next` فقط وقتی دادهٔ بیشتری وجود دارد مقدار می‌گیرد. درخواست بعدی همان شناسه/شماره و بازه را نگه می‌دارد و این دو پارامتر را اضافه می‌کند:

```http
GET /messages?billId=00123&fromJalali=1405/07/01&toJalali=1405/07/30&beforeDate=1405/07/20&beforeId=12300
X-Api-Key: YOUR_CUSTOMER_API_KEY
```

اگر `next` برابر `null` باشد، صفحهٔ دیگری وجود ندارد. نبود نتیجه، پاسخ موفق با `items: []` است. هر صفحه دوباره به مشتری کلید محدود می‌شود؛ تغییر شناسهٔ cursor باعث دسترسی به پیام‌های مشتری دیگر نمی‌شود. وضعیت‌ها ممکن است هنگام مرور توسط پردازش ارسال/تحویل تغییر کنند.

این API همهٔ پیام‌های خروجی ثبت‌شده را با وضعیت فعلی‌شان برمی‌گرداند، از جمله پیام‌های در صف یا ردشده؛ فقط پیام‌های موفق نیستند. مقادیر `status`: در صف `1`، ثبت ارائه‌دهنده `2`، ارسال‌شده `3`، ردشده `4`، نامشخص `5`، انتظار تأیید `6`. مقادیر `deliveryStatus`: در انتظار `1`، تحویل‌شده `2`، تحویل‌نشده `3`، منقضی `4`، نامشخص `5`.

اگر متن بر اساس سیاست نگهداری زودتر حذف شده باشد، `body` برابر `null` است و خود پیام همچنان در نتیجه باقی می‌ماند. پاسخ با `Cache-Control: no-store` ارسال می‌شود.

## خطاها

- `400`: پارامتر نامعتبر، نبود شناسه، ارسال هم‌زمان دو شناسه، تاریخ نامعتبر یا cursor ناقص.
- `401`: کلید ارائه نشده یا احراز هویت کلید ناموفق است؛ شامل انقضا، ابطال و عدم تطابق IP.
- `403`: کلید ارائه‌شده کلید مشتری نیست.

جزئیات خطا و شناسهٔ پیگیری در قالب معمول API برگردانده می‌شوند. مسیرهای موجود ارسال (`POST /messages`) و گزارش‌های مدیریتی تغییری در قرارداد احراز هویت خود ندارند.
