# 4040 via ESB

The provider business code is `4040`. It is independent of Magfa; a `4040` prefix alone does not select this provider or ESB routing. Register the provider as reference data, define its tariffs normally and enable **ارسال از طریق ESB** on the required sender lines (`SenderLine.UseEsb`). Existing lines retain `UseEsb = false` through additive migration `0032`.

When `DevelopmentSeed:Enabled` is true in Development, startup also seeds provider `4040` and sender line `40401403` for the default development customer with `UseEsb = true`. It adds fallback tariffs for GSM-7 and UCS-2 at **1,500 IRR per segment**, exclusively as a development test price. Rerunning seed does not duplicate these records. Restart the app, choose `40401403 — 4040` at `/admin/send`, enter the intended recipient/text, quote and submit. Submission uses the real configured ESB; successful submission alone does not establish delivery.

Configuration is in the `Esb` section of the main host's appsettings. The tracked file contains blank credentials and `Enabled = false`. The supplied development credentials are saved in the gitignored `appsettings.Development.local.json`, which overrides those defaults. Configure deployment credentials in the corresponding local configuration or environment variables.

```json
{
  "Esb": {
    "Enabled": true,
    "LoginUrl": "https://esb.abfaisfahan.com:8243/token",
    "SendUrl": "https://esb.abfaisfahan.com:8243/Nww-SendSms/1.0",
    "DeliveryUrl": "https://esb.abfaisfahan.com:8243/Nww-CheckDeliverySms/1.0",
    "TerminalDeliveryStatuses": { "1": "Delivered" },
    "Username": "YOUR_CLIENT_ID",
    "Password": "YOUR_CLIENT_SECRET",
    "Timeout": "00:00:30"
  }
}
```

Login is an HTTPS POST with Basic authentication and an `application/x-www-form-urlencoded` body containing `grant_type=client_credentials`. `Username` is the OAuth client id; `Password` is the client secret. `EsbAccessTokenProvider` is a singleton shared by dispatch requests. It uses a lock around login, reuses the token while valid, and derives expiry from the start of login plus `expires_in`. This conservatively includes login latency without inventing a fixed one-hour lifetime. The next operation after expiry obtains a new token. Invalid/failed login responses are not cached. Tokens remain in memory and are neither persisted nor logged; a process restart obtains a new token. Each application process has its own cache.

Send uses the configured ESB URL, Bearer authentication, and the supplied parallel arrays: `senders`, `messages`, `recipients`, and `uids`. The UID is the durable local message id. Iranian recipients normalized as `989…` internally are converted back to the demonstrated `09…` form for 4040. Success requires outer `status.statusCode = 200`, `result.status.statusCode = 200`, `result.data.status = 0` and the expected number of non-empty `smsids`. IDs are preserved unchanged in `Message.ProviderMessageId`, subject to its existing ASCII/50-character storage contract.

Only the one-message contract has been demonstrated, so the dispatcher submits one message per upstream request until a batch limit and response-order guarantee are supplied. Pricing, debit, attribution and idempotency remain in the existing acceptance handler. An ESB line does not require a direct `ProviderAccount`; other providers retain their existing credential checks. ESB disabled or an unsupported direct 4040 route is rejected before accounting debit.

Login failures occur before SMS submission and are returned as known-not-submitted retryable outcomes. Gateway HTTP 401/403 is a definitive authentication refusal. After an SMS request is sent, transport errors, timeouts, unexpected HTTP responses, undocumented nonzero business codes and malformed/mismatched responses leave the outcome unknown. The existing dispatcher keeps such messages awaiting confirmation and then holds them for manual review, without automatic resend: no 4040 idempotent resend or UID lookup contract has been supplied.

Delivery polling posts `{"_body":["FULL_SMS_ID"]}` to `Esb:DeliveryUrl` with the same cached Bearer token, JSON content/accept headers and the required gateway workaround header `basicAuthorization: Basic bugfix`. That placeholder carries no credentials. Each distinct ID is queried separately until a bulk limit is documented. All three response success markers are checked, and `result.data.dlrs` is matched by the full requested smsId. Returned `uid`, `DateSent` and `DateDlr` are read from the payload but do not replace the durable message ID or the poller's UTC observation timestamps.

The meanings of provider `dlr` codes have not been documented. At the project owner's explicit request, **code `1` is provisionally treated as Delivered**, rather than claimed to be a verified provider rule. `Esb:TerminalDeliveryStatuses` makes this assumption adjustable and maps provider codes to the application's `DeliveryReportStatus` values (`Delivered`, `Undelivered`, `Expired`, `Rejected`, `Unknown`). Other codes are not guessed from the internal enum. Unmapped codes and absent IDs remain pending and are polled again; malformed entries, invalid JSON, unsuccessful status markers, HTTP errors and timeouts fail the query for a later retry. Mapped terminal results use the existing poller to update current message status and append delivery history through its normal guarded transaction. No status/credit/inbox endpoint from Magfa is reused.

No inbox, credit, direct 4040 API or uncertain-submission lookup by local UID has been supplied. These are not inferred from the delivery query (which requires an already-known smsId); automatic resend remains disabled.
