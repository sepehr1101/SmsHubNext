# 4040 via ESB

## Classified failures (2026-11-01)

4040 failures carry allow-listed `OperationFailure` fields: origin (application, network, ESB gateway or SMS provider), stage (validation, token, submission or delivery query), stable internal code, impact and next action. Actual HTTP status, failed envelope status and provider business status are separate nullable values; HTTP 200 with a nonzero business status is not an HTTP failure. A nonzero business status is attributed to the SMS provider only when both gateway envelope markers succeed. Codes are evidence, not an inferred rejection/refund taxonomy.

Migration 0038 adds nullable, bounded `MessageBatchEvent.FailureJson`. Dispatch and polling write event type 13 once per affected batch per failure, using the existing operational retention; successful paths add no diagnostic writes. The message diagnostic panel and copied report show the fields in Persian. Live queries return the same structured diagnostics without writing history. Token failures during polling have delivery-query-unavailable impact even though their stage is token acquisition. Failed polling never marks messages undelivered. Legacy events remain unclassified. No response bodies, exception text, Authorization headers, credentials or tokens enter the structured payload.

This increment covers 4040 and message diagnostic details; it does not add global origin/stage dashboard filters or historical backfills.

The provider business code is `4040`. It is independent of Magfa; a `4040` prefix alone does not select this provider or ESB routing. Register the provider as reference data, define its tariffs normally and enable **ارسال از طریق ESB** on the required sender lines (`SenderLine.UseEsb`). Existing lines retain `UseEsb = false` through additive migration `0032`.

When `DevelopmentSeed:Enabled` is true in Development, startup also seeds provider `4040` and sender line `40401403` for the default development customer with `UseEsb = true`. It adds fallback tariffs for GSM-7 and UCS-2 at **1,500 IRR per segment**, exclusively as a development test price. Rerunning seed does not duplicate these records. Restart the app, choose `40401403 — 4040` at `/admin/send`, enter the intended recipient/text, quote and submit. Submission uses the real configured ESB; successful submission alone does not establish delivery.

Configuration is in the `Esb` section of the main host's appsettings. The tracked file contains blank credentials and `Enabled = false`. The supplied development credentials are saved in the gitignored `appsettings.Development.local.json`, which overrides those defaults. Login is an HTTPS POST with Basic authentication and an `application/x-www-form-urlencoded` body containing `grant_type=client_credentials`. `Username` is the OAuth client id; `Password` is the client secret. `EsbAccessTokenProvider` is a singleton shared by dispatch requests. It uses a lock around login, reuses the token while valid, and derives expiry from the start of login plus `expires_in`. This conservatively includes login latency without inventing a fixed one-hour lifetime. The next operation after expiry obtains a new token. Invalid/failed login responses are not cached. Tokens remain in memory and are neither persisted nor logged; a process restart obtains a new token. Each application process has its own cache.

Send uses the configured ESB URL, Bearer authentication, and the supplied parallel arrays: `senders`, `messages`, `recipients`, and `uids`. The UID is the durable local message id. Iranian recipients normalized as `989…` internally are converted back to the demonstrated `09…` form for 4040. Success requires outer `status.statusCode = 200`, `result.status.statusCode = 200`, `result.data.status = 0` and the expected number of non-empty `smsids`. IDs are preserved unchanged in `Message.ProviderMessageId`, subject to its existing ASCII/50-character storage contract.

Per the user decision on 2026-10-31, the dispatcher submits up to **100 messages per upstream request**. Larger batches are split into chunks of 100 plus the remaining messages (for example, 250 messages use requests of 100, 100 and 50). Returned `smsids` are mapped in request order; the response must contain exactly one distinct valid ID per message. Pricing, debit, attribution and idempotency remain in the existing acceptance handler. An ESB line does not require a direct `ProviderAccount`; other providers retain their existing credential checks. ESB disabled or an unsupported direct 4040 route is rejected before accounting debit.

Login failures occur before SMS submission and are returned as known-not-submitted retryable outcomes. Gateway HTTP 401/403 is a definitive authentication refusal. On HTTP 401 from send or delivery polling, the shared cache invalidates only the token used by that request, under the login lock; a late refusal for an old token cannot evict its replacement. The next operation obtains a fresh token through the existing serialized login. Send HTTP 401 is known-not-submitted and retryable through the dispatcher's persisted attempt budget with the original UID; there is no hidden inline submission retry or reset of counters/window. Repeated 401 responses eventually exhaust that budget and hold the batch for review. HTTP 403 retains the permanent refusal behavior and does not refresh the token. Delivery HTTP 401 remains a failed query for the normal poll retry, never evidence of handset delivery failure. After an SMS request is sent, transport errors, timeouts, unexpected HTTP responses, undocumented nonzero business codes and malformed/mismatched responses leave the outcome unknown. The user confirmed on 2026-10-19 that 4040 deduplicates the same UID for 24 hours. The dispatcher may retry an uncertain submission with the original durable message ID as UID within that window, without a UID lookup. The window starts at the first attempt and never resets on retry. A duplicate or malformed response without a valid smsId remains uncertain; it does not establish acceptance or handset delivery.

Delivery polling posts `{"_body":["FULL_SMS_ID_1","FULL_SMS_ID_2"]}` to `Esb:DeliveryUrl` with the same cached Bearer token, JSON content/accept headers and the required gateway workaround header `basicAuthorization: Basic bugfix`. That placeholder carries no credentials. All three response success markers are checked, and `result.data.dlrs` is matched by the full requested smsId, independently of response order; unrequested IDs are ignored. Returned `uid` does not replace the durable message ID. `DateSent` and `DateDlr` are preserved as raw strings in live diagnostic results; their format/unit/time zone is not inferred, and they do not replace the poller's UTC observation timestamps. Numeric status fields also accept numeric JSON strings as described in the supplied contract. An absent ID is explicitly marked as having no provider status, distinct from a real DLR code `0`.

Per the user request on 2026-11-01, `Esb:UseBatchDeliveryQueries` defaults to `true`. Distinct IDs are split into chunks of `Esb:DeliveryQueryBatchSize` (default 100; configurable from 1 to 100). This is an application-selected size for trial, **not a confirmed gateway delivery-query limit**; validate multi-ID responses against the real ESB before relying on the throughput improvement. The poll worker's own `DeliveryReportPolling:BatchSize` still limits how many pending messages it claims per cycle, so larger upstream chunks cannot exceed the available IDs in a provider group. Empty input makes no upstream request. Malformed responses or entries fail the operation for the existing poll retry; missing IDs remain pending. No automatic single-ID fallback masks batch failures.

To roll back, set `Esb:UseBatchDeliveryQueries` to `false` in the environment-specific local configuration (or `Esb__UseBatchDeliveryQueries=false`) and restart the host. The retained individual-query method then sends one request per distinct ID, using the same authentication, response mapping and retry semantics. No schema change or redeployment is needed to switch modes. Reducing `DeliveryQueryBatchSize` is also possible without a code change; size 1 uses single-ID requests through the batch path.

The supplied Khat Roshan document, pages 14–15 (table 5-8), documents the provider `dlr` meanings. **Code `1` means delivered to the handset**, confirming the existing mapping. The management message diagnostic view interprets all listed codes in Persian, including intermediate, archive and refund-related codes. Displaying these meanings does not change terminal-state or accounting rules; finality/transition guarantees and refund reconciliation still need clarification. `Esb:TerminalDeliveryStatuses` makes this assumption adjustable and maps provider codes to the application's `DeliveryReportStatus` values (`Delivered`, `Undelivered`, `Expired`, `Rejected`, `Unknown`). Other codes are not guessed from the internal enum. Unmapped codes and absent IDs remain pending and are polled again; malformed entries, invalid JSON, unsuccessful status markers, HTTP errors and timeouts fail the query for a later retry. Mapped terminal results use the existing poller to update current message status and append delivery history through its normal guarded transaction. No status/credit/inbox endpoint from Magfa is reused.

No inbox, credit, direct 4040 API or uncertain-submission lookup by local UID has been supplied. These are not inferred from the delivery query (which requires an already-known smsId); UID-based submission retries use the bounded guarantee above; delivery still requires a known smsId.

## Submission retry budget (2026-10-19)

All providers allow at most one initial dispatch plus three retries per stored message. Migration 0035 adds SendAttemptCount and FirstSendAttemptAtUtc, recorded atomically before calling the provider. A crash can consume an attempt even before transport completes; this conservative accounting never expands the budget. Batch claims, confirmation lookups and delivery polling are not submission attempts. Requeue and manual batch retry do not reset these fields. This is distinct from the explicit resend endpoint, which creates a new message and is still blocked for uncertain outcomes.

At the limit, or at/after 24 hours for 4040, the batch is Held for manual review; uncertain messages are not rejected/refunded or marked delivered. Credit-blocked attempts also consume the budget. Existing rows have no exact historical per-message counter: their previous batch attempt count is used as a conservative upper bound and the batch start as the earliest retry-window anchor. No historical acceptance time is fabricated and no cold-partition backfill is performed. Previously Held manual-review batches remain held after deployment.
